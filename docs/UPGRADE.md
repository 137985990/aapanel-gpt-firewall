# 既有 free_waf 5.0 的升级与恢复

本教程用于 **aapanel GPT Firewall v0.1.1** 社区兼容升级。只操作已经安装并正常运行的 aaPanel `free_waf 5.0` 或本社区版本，不支持空机器首次安装。请先在测试环境完成恢复和升级演练。

旧 v0.1 没有更新入口，需按本教程手动上传一次 v0.1.1。此后可使用 [更新管理](UPDATES.md) 检查社区版本并确认一键更新；不要使用旧插件商店的更新覆盖社区版本。

## 一、确认能否升级

- 确认内部插件名是 `free_waf`，原插件目录 `/www/server/panel/plugin/free_waf`、运行目录 `/www/server/free_waf` 和旧数据完整。
- 记录当前面板、Nginx、Lua 与 Python 版本、启用站点、必要模块和原有配置引用关系。缺少模块、库、规则或运行数据时应停止，不运行旧安装器补齐。
- 确认这不是付费 WAF，也不是中文 8.x。若有其他防火墙或重复的 Lua 集成，先停止本次升级并单独确认兼容性。本包不会自动禁用其他插件。
- 本预发布尚未验收未经修改的原生 5.0 还原环境。插件内已有扫描器 `rule.json`，运行目录内的 `header`、`user_agent_white` 等规则文件也是预检条件；旧版本号相同并不等于可直接升级。缺少时停止，不创建空规则绕过检查。
- 保留独立的服务器管理通道与回退窗口。升级期间暂停后台规则编辑、批量站点变更等管理操作，避免与安装交错写入。

ZIP 中仍使用 `free_waf` 插件名和兼容目录；这是原位升级，不是并排安装第二个插件。不要改 ZIP 内的目录、类名或插件标识来强行导入。

## 二、上传之前备份

**必须先备份，再向面板上传。** 面板导入可能在运行安装钩子前覆盖后端等插件文件，钩子自己的备份无法补回这一步之前的旧版本。

至少保留以下内容，放在只有管理员可读的位置，不提交到公开仓库或问题区：

| 内容 | 默认位置与注意事项 |
| --- | --- |
| 旧插件完整目录 | `/www/server/panel/plugin/free_waf`，包括旧后端、页面、元数据、脚本及附带文件 |
| 旧运行完整目录 | `/www/server/free_waf`，包括 Lua、配置、规则、黑白名单、站点配置及目录内日志 |
| 宝塔 Nginx 配置 | `/www/server/nginx/conf`，保留主配置与相关引用文件 |
| 面板站点与包含文件 | `/www/server/panel/vhost/nginx`，并检查其引用的其他目录和自定义文件 |
| 外置数据与依赖 | 另设日志目录、自定义规则、符号链接目标及配置引用的其他文件，需要另行盘点与备份 |

以下仅是默认目录的备份示例，不执行安装、卸载或重载；不适合缺少旧运行目录的机器：

```sh
set -eu
test -d /www/server/panel/plugin/free_waf
test -d /www/server/free_waf
test -d /www/server/panel/vhost/nginx
test -x /www/server/nginx/sbin/nginx
/www/server/nginx/sbin/nginx -t

umask 077
backup="/root/gpt-firewall-backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p /root/gpt-firewall-backups
mkdir "$backup"
tar -czpf "$backup/plugin.tgz" -C /www/server/panel/plugin free_waf
tar -czpf "$backup/runtime.tgz" -C /www/server free_waf
tar -czpf "$backup/nginx-config.tgz" -C / www/server/nginx/conf www/server/panel/vhost/nginx
printf '%s\n' "$backup"
```

确认备份可读、空间充足，并另行备份符号链接指向的外部文件；示例不会自动追踪所有外部依赖。若同名备份目录已经存在，示例会停止而不覆盖原备份。保留面板和 Nginx 的当前健康记录。持续写入的日志与临时封禁不是事务性快照，目录备份也不包含全部 Nginx 共享内存状态。

若升级前宝塔 Nginx 配置检查已经失败，先解决原有问题，不能把升级当成修复任意旧环境的手段。

## 三、通过面板上传 ZIP

1. 使用明确标注为 v0.1.1、针对既有 `free_waf 5.0` 或社区版本的升级包，核对发布说明和提供的校验值。没有验收记录的源码压缩包不要当成可直接安装包。
2. 在 aaPanel 第三方插件的 ZIP 上传／导入入口选择升级包。不同面板版本入口名称可能不同，不通过卸载旧插件来获得入口。
3. 由面板解压并执行包内安装钩子，完整保留安装输出。不要同时升级 Nginx、替换其他 WAF 或修改规则。
4. 检查 `/www/server/panel/plugin/free_waf/install-status.json`，确认记录属于本次尝试，而不是上次残留。保存前后的修改时间及安装输出，具体字段以该发布包的实际记录为准。

安装器应使用包内文件，不抓取上游安装器或规则，不覆盖原有规则、站点配置、黑白名单和日志；依赖不足时停止。离线约定只约束本安装器，面板上传处理及原有界面的网络行为不在此保证内。

**不要执行旧版卸载脚本，不要先卸载再导入，也不要运行从旧论坛帖子取得的安装命令。** 它们不是本兼容升级的恢复步骤，可能改写或删除现有数据。

## 四、检查状态与业务

状态记录至少需要能说明本次是否成功、宝塔 Nginx 配置检查结果、是否尝试启用以及失败后的回退结果。若记录缺失、时间不符、显示失败或只表明部分回退，请按失败处理；面板弹出成功提示不能替代这些核对。

本版状态约定中的重点字段：

| 字段 | 核对方式 |
| --- | --- |
| `status` | `success` 表示安装钩子报告成功；`failed` 需要排查，不继续扩展上线 |
| `version`、`plugin_name` | 应对应本次项目版本 `0.1.1` 和兼容插件名 `free_waf` |
| `waf_active` | `false` 不等于防火墙已经启用；即使代码升级成功，仍需核查原有集成和业务状态 |
| `runtime_changed` | 表示本次是否替换运行时代码，不代表所有防护状态已经验证 |
| `plugin_rollback_available` | `false` 提醒钩子无法恢复导入前的插件文件，需要上传前的独立备份 |
| `rollback` | `restored` 只表示所管理范围已恢复；`restore_reload_failed` 表示恢复后的重载仍失败，不能当作完整回退成功 |

`status`、代码回退和业务恢复是不同层面的结果。即使 `rollback` 表示恢复，也不能据此忽略仍为失败的安装状态。

1. 用实际宝塔二进制检查配置，不用系统路径中可能存在的另一个 Nginx：

```sh
/www/server/nginx/sbin/nginx -t
```

2. 确认 Nginx 实际运行、站点可访问，面板能打开插件且没有后端报错；必要时按面板实际机制刷新插件加载，不把重启服务当成默认排错步骤。
3. 检查原规则、站点开关、例外与黑白名单仍存在，日志持续写入。使用备份或升级前的私下记录核对，勿把这些内容贴到公开问题中。
4. 在测试站点和隔离夹具中验证注册封禁能够列出、正确解除且后续请求恢复；验证全局停用规则后，站点例外仍指向目标规则，不误停其他规则。
5. 回归测试站点的正常登录、注册、接口、上传及使用中的流式响应等业务。先观察有限范围，再逐站点验证；不要向生产站点发送攻击载荷来代替隔离回归。

本教程没有执行上述环境验收，也没有给出所有生产站点通过的保证。状态成功但业务异常时，同样应停止扩展上线并检查或回退。

## 五、失败与人工恢复

安装钩子应在宝塔 Nginx 配置检查或启用失败后，尝试恢复本次替换的运行时代码并记录结果。它不能保证恢复上传前已被面板覆盖的后端、页面和元数据，也不能恢复任意时刻的内存封禁状态。

1. 停止重复上传与并发配置变更，保留本次状态记录和脱敏错误信息。不要卸载插件，不自动停用其他防护。
2. 从上传前的插件备份恢复本次覆盖的代码、页面、元数据和随包文件。按文件清单操作，不盲目解压全部备份覆盖当前数据。
3. 核对运行时代码是否已经回退。若没有，仅恢复本次替换的代码；不要用旧运行目录整包覆盖现有配置、规则、黑白名单或日志。
4. 只有确认本次修改了某个 Nginx 引用文件且需要恢复时，才从备份取回该文件；不要回滚无关站点和同期合法变更。
5. 再次运行 `/www/server/nginx/sbin/nginx -t`。只有配置检查通过，才考虑通过面板实际机制平滑重载；检查失败时不要重启或重载来碰运气。
6. 重新检查面板、测试站点、日志和封禁状态。若回退仍失败，保留可用服务与独立管理通道，停止自动操作并请求人工排查。

数据备份用于核对和有针对性的恢复，不是自动回滚时恢复旧黑名单、复活过期封禁或抹去升级期间日志的理由。遇到确需恢复数据的情况，应先逐项确认时间范围和后果。

## 六、反馈与剩余风险

JSON 并发写入、正文解析覆盖和 CDN 信任配置仍需要单独评估。升级两个缺陷并不意味着路线图全部完成，也不保证所有面板与全部站点适配。

通过本仓库 GitHub Issues 提交问题时，提供版本、可复现步骤及脱敏后的状态摘要即可。敏感证据先请求私下安全沟通渠道；不要公开生产地址、账号、密钥、原始请求或完整日志。
